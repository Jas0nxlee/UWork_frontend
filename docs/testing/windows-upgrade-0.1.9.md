# 0.1.9 升级修复验证

## 根因与修复

旧版安装资源可能留下空 `node_modules/koffi` 或 `node_modules/sharp` 目录。0.1.8 的官方 Computer Use 定义仍将两者列为运行依赖根，加载时读取不存在的 `package.json`，使插件发现和草稿创建失败。当前 producer 0.6.5 已不依赖两者；修复删除过时定义，继续严格校验实际必需的 SDK 资产和依赖闭包。现场通用提示不能作为数据库被锁定的证据。

## Windows 虚拟机完整升级

2026-11-05，在 Windows 11 ARM 虚拟机中运行 x64 客户端。每条路径先安装正式旧版本，通过界面创建会话并收到真实模型回复，再安装目标版本，检查旧消息和新消息。修复候选为源码提交 `1042cba7` 构建的 `0.1.9-test.1`；不是已发布的正式 0.1.9 安装包。

| 起始版本 | 目标版本   | 旧消息 | 新建会话发送消息             | 结果来源                 |
| -------- | ---------- | ------ | ---------------------------- | ------------------------ |
| 0.1.2    | 正式 0.1.8 | 保留   | 草稿创建失败，复现问题       | 虚拟机界面与日志         |
| 0.1.2    | 修复候选   | 可见   | 收到模型回复，重启后继续回复 | 虚拟机界面与日志         |
| 0.1.5    | 正式 0.1.8 | 可见   | 收到模型回复                 | 用户按交互步骤操作并确认 |
| 0.1.5    | 修复候选   | 可见   | 收到模型回复                 | 用户按交互步骤操作并确认 |
| 0.1.6    | 正式 0.1.8 | 可见   | 收到模型回复                 | 用户按交互步骤操作并确认 |
| 0.1.6    | 修复候选   | 可见   | 收到模型回复                 | 用户按交互步骤操作并确认 |

旧版测试前隔离会话数据库和索引，保留账号配置；0.1.6 拒绝新版 `discoveredProviderModelRules` 字段时，备份并隔离新版模型配置后建立旧版基线。这是避免降级配置污染的测试准备，不属于本次产品修复。0.1.2 → 0.1.8 的失败路径已确认历史会话迁移保留相同 ID，而插件加载仍因空 Koffi 目录失败。

这些结果不能代替原生 Windows x64 硬件覆盖，也不作为重新登录流程的验收。

## macOS 同类条件

复制实际安装的 macOS ARM64 0.1.8 资源，在隔离的用户目录、存储和工作目录中运行插件发现；不修改原有安装或真实用户数据。使用 Node 24.14.0 和实际 Electron 42.11.16 的 Node 24.19.0 各执行一轮，结果一致：

| 资源条件           | 0.1.8 原版            | 修复候选 CLI |
| ------------------ | --------------------- | ------------ |
| 无遗留原生依赖目录 | 通过                  | 通过         |
| 空 Koffi 目录      | `package.json` ENOENT | 通过         |
| 空 Sharp 目录      | `package.json` ENOENT | 通过         |

此结果验证共享修复在 macOS 的效果，没有执行 Mac 旧版本到新版本的完整 GUI 安装升级。macOS 的整包更新机制不同于 Windows NSIS，不能据此断言正常 Mac 更新必然产生相同残留。
